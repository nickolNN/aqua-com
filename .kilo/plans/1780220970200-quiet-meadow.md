# End-to-End Testing with Playwright

## Goal

Create end-to-end tests for the Aqua CRM auth system (login, register, password reset, route guard) using Playwright, running against Google Chrome with a local dev server.

## Setup

### 1. Install Playwright dependencies

Install Playwright and its browser binaries:
- `npm install -D @playwright/test`
- `npx playwright install chromium` (or `npx playwright install chromium --with-deps` for system deps)

### 2. Create Playwright config

Create `playwright.config.ts` with:
- `testDir` pointing to `src/frontend/tests` (or `src/frontend/e2e`)
- `use` block with `chromium` browser, headless mode, and viewport dimensions matching typical desktop
- `testMatch` pattern matching `**/*.spec.ts` or `**/*.spec.ts`
- `webServer` config to start Vite in development mode on port 3000 before running tests, using `npm run dev` in `src/frontend`
- `timeout` settings and `retries` configuration
- `reporter` setup (e.g., `list` for CI, `html` for local)

### 3. Create test directory structure

```
src/frontend/tests/e2e/
  auth.spec.ts
  login.spec.ts
  register.spec.ts
  password-reset.spec.ts
  auth-protected-routes.spec.ts
  playwright.config.ts
```

## Test Configuration (`playwright.config.ts`)

- Use Playwright's config format with `project` section for Chromium
- Configure `webServer` to serve the Vite dev server at port 3000 before tests
- The dev server uses `cd src/frontend && npm run dev` with port 3000
- The Vite config has an alias `@` → `src/frontend/src/` and proxy to `localhost:8000` for `/api`
- Enable `use` block with `chromium`, `headless: true` (but works in headed Chrome with `playwright test --ui` or `playwright test --grep`)
- Set `baseURL` to `http://localhost:3000`

## Test Setup & Teardown

### Before each test:
- Navigate to the app's base URL
- The app starts in mock mode (since `setMockMode(true)` is called in `main.tsx`)
- Clear localStorage before each test using `page.evaluate()` to ensure isolation between tests

### Teardown:
- No cleanup needed; Playwright handles page closure

## Test Files

### `auth/login.spec.ts`

#### Test 1: Login with valid credentials
1. Navigate to `/login`
2. Fill email field (`#email`) with `test@example.com`
3. Fill password field (`#password`) with any value (e.g., `password123`)
4. Click submit button (`button[type="submit"]` or `button:has-text("Sign in")`)
5. Verify navigation to `/` (dashboard) — check URL or presence of dashboard elements
6. Verify token was stored in localStorage (`localStorage.getItem('token')`)

#### Test 2: Login with invalid credentials
1. Navigate to `/login`
2. Fill email and password fields
3. Click submit
4. Verify error message is displayed (server error handling)
5. Verify form still shows with the entered values

#### Test 3: Login form validation (empty fields)
1. Navigate to `/login`
2. Click submit without entering any data
3. Verify validation errors appear ("Email is required", "Password is required")

### `auth/register.spec.ts`

#### Test 1: Register with valid data
1. Navigate to `/register`
2. Fill name field (`#name`) with `Test User`
3. Fill email field (`#register-email`) with `newuser@example.com`
4. Fill password (`#password`) with `TestPass123`
5. Fill confirm password (`#confirm-password`) with `TestPass123`
6. Click submit (`button[type="submit"]` or `button:has-text("Create account")`)
7. Verify navigation to `/login`
8. Verify success/error behavior

#### Test 2: Register form validation
1. Navigate to `/register`
2. Fill incomplete data (name but missing password)
3. Submit and verify validation errors appear

#### Test 3: Register with mismatched passwords
1. Fill all fields but use different passwords
2. Submit and verify "Passwords do not match" error

### `auth/password-reset.spec.ts`

#### Test 1: Password reset page
1. Navigate to `/password-reset`
2. Fill email field with a valid email format
3. Click submit
4. Verify success state with "Check your email" message and link back to login

#### Test 2: Password reset form validation
1. Navigate to `/password-reset`
2. Submit without entering email
3. Verify validation errors appear

### `auth/auth-protected-routes.spec.ts`

#### Test 1: Unauthenticated user redirects to login
1. Navigate to `/` (dashboard) while logged out
2. Verify redirect to `/login`
3. Verify `state={{ redirectFrom: "/" }}` on the login page (check `window.location.state` or the login page renders with redirect state)

#### Test 2: After login, access protected routes
1. Login (as defined in login tests)
2. Navigate to `/contacts`
3. Verify page loads correctly
4. Repeat for `/companies`, `/tasks`, `/activities`

## Running Tests

### Run all tests:
```bash
npx playwright test
```

### Run a single test file:
```bash
npx playwright test src/frontend/tests/e2e/auth/login.spec.ts
```

### Run tests with headed browser (for debugging):
```bash
npx playwright test --headed
# or use the Playwright UI
npx playwright test --ui
```

### Run a specific test:
```bash
npx playwright test --grep "login with valid credentials"
```

### Generate Playwright UI screenshot on failure:
```bash
npx playwright test --retries=3
```

### Playwright codegen for recording tests:
```bash
npx playwright codegen http://localhost:3000/login
```

## Notes

- The app runs with **mock mode enabled** (`setMockMode(true)` in `main.tsx`), so all API calls hit MSW handlers
- Login mock returns `{ token: 'mock-jwt-token', user: {...} }`
- Register mock returns `{ token: 'mock-jwt-token', user: {...} }`
- The `PrivateRoute` component checks Redux state (`selectIsAuthenticated`) but NOT the mock interceptors directly — it uses `useSelector` from Redux
- For protected route tests, note that `PrivateRoute` uses Redux state, but the login flow stores only a token in localStorage (NOT Redux state), so the protected route check may not work correctly. Consider: either updating the test to navigate after login or using a different assertion (e.g., check that the page renders rather than Redux auth state).
- The Vite dev server proxy (`/api` → `localhost:8000`) intercepts `/api/*` routes, but MSW also intercepts `/api/*` routes in the browser — so both the mock interceptors (RTK Query mock mode) and MSW handlers work.
